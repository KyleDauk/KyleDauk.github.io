Enhancement One: Software Design and Engineering

Version 2.0 of the Weight Tracking Android app I built in CS 360: Mobile Architecture and Programming. It re-architects the app around MVVM with a repository layer, replaces unsalted password hashing with PBKDF2, adds sessions, centralized validation, and privacy fixes, and is covered by 87 automated tests that run on every push.

Browse the enhanced code (v2.0) Compare with the original (v1.0 to v2.0) Original CS 360 code (v1.0)

At a glance

Architecture

MVVM: Activities display data, ViewModels hold screen state, and one repository does all database work on a background thread.

Security

Salted PBKDF2 with 600,000 iterations, account lockout, a 15-minute session timeout, and no SMS permission or stored phone numbers.

Quality

87 JUnit and Robolectric tests, Android Lint with zero errors, and a GitHub Actions workflow that runs them on every push.

Narrative

Artifact Description

The artifact is Weight Tracking, an Android application written in Java that I built as the final project for CS 360: Mobile Architecture and Programming during the 2026 C-4 term (June to August 2026). Users create an account, log their body weight by date, set a goal weight, and record waist, hip, and height measurements from which the app calculates body mass index (BMI) and waist-to-hip ratio. Version 1.0 stored all data in a local SQLite database, displayed the weight history in a RecyclerView grid with a change column and a goal summary, and sent a text message through SmsManager when a saved weight reached the goal.

For Enhancement One, I re-architected the application and hardened its security, following the plan approved in Module One and the findings from my Milestone One code review. Version 2.0 contains 37 production Java classes, 14 test files (11 test classes and 3 test helpers), a GitHub Actions workflow, and an architecture README. Across 66 files, the change adds about 5,800 lines and removes about 1,500. The v1.0 tag of the repository holds the untouched CS 360 project, and the v2.0 tag holds this enhancement.

Justification for Inclusion

I selected this artifact because it is a complete, working mobile application that still showed every weakness a professional code review is meant to find. Each screen worked in a demonstration, but every Activity mixed user interface code, input validation, business rules, and SQL, and every database call ran on the main thread. Passwords were stored as unsalted SHA-256 hashes and compared with String.equals. Users could make unlimited login attempts, sessions never expired, and the app held the restricted SEND_SMS permission and a stored phone number. Health data could leave the device through backups, and the database upgrade routine dropped every table. Correcting these problems required design decisions across the whole codebase rather than a single feature, which makes the artifact a strong showcase for my career goal of working as a remote mobile and full-stack software engineer.

Components That Showcase Software Engineering Skills

Layered MVVM architecture. Each data screen now has a ViewModel that exposes LiveData, and the Activities only bind that state to views and forward taps. The ViewModels depend on a TrackerRepository interface rather than on SQLite. The production SqliteTrackerRepository runs every query on a single background thread and delivers results on the main thread. A small AppContainer wires the dependencies by constructor injection, and a ViewModelFactory passes them to each ViewModel. This structure follows Google's recommended separation between a UI layer and a data layer (Android Developers, n.d.-a), and it means the planned Room migration in Enhancement Three can replace the storage class without touching any screen.

Secure authentication. PasswordHasher derives keys with PBKDF2WithHmacSHA256, using a 16-byte salt from SecureRandom and 600,000 iterations, the current OWASP recommendation for that algorithm (OWASP Foundation, n.d.). It compares hashes in constant time with MessageDigest.isEqual. AuthService locks an account for 15 minutes after five failed attempts and returns the same message for an unknown username and a wrong password. It also performs one full hash in both cases, so a single login attempt reveals neither through its message nor through its response time whether a username exists. Repeated failures can still reveal it, because only a real account can be locked. I accepted that trade-off because the lockout is what stops password guessing. Existing version 1.0 accounts are not broken. Their SHA-256 hash is verified once at the next successful login and immediately replaced with a salted PBKDF2 hash.

Session management. SessionManager is now the single source of truth for the signed-in user, replacing the user id that version 1.0 copied through every Intent. A SecureActivity base class checks the session whenever a protected screen is created or resumed and at the start of every touch, so it returns the user to the login screen after 15 idle minutes even if the screen was left on. Every touch counts as activity. A new Log out menu item ends the session and clears the back stack, so pressing Back cannot reveal the previous user's data.

Defensive programming. InputValidator centralizes every rule: weights and goals between 50 and 1,000 pounds, plausible ranges for waist, hip, and height, no future dates, a username pattern, and a password policy. The rules are free of Android types so they can be unit tested. Database writes now report failure, so a failed save shows an error and keeps the form open instead of displaying a false "Weight saved" message. Update and delete statements match on both the row id and the signed-in user's id, so a wrong id can never change another user's data.

Privacy and least privilege. GoalNotifier replaces SMS with a local notification and requests the POST_NOTIFICATIONS runtime permission that Android 13 introduced (Android Developers, n.d.-c). SEND_SMS and the phone number field were removed, and the database upgrade erases phone numbers already stored. The notification is marked private, so a locked phone shows only a generic "Weight Tracking update" message. Backups are disabled, and the data extraction rules also exclude the database from device-to-device transfer, which allowBackup="false" alone does not prevent on Android 12 and later (Android Developers, n.d.-b).

Non-destructive database upgrade. Schema version 2 adds the salt, hash_version, failed_attempts, and locked_until columns with ALTER TABLE inside onUpgrade. SQLiteOpenHelper runs the upgrade in a transaction, so existing users, weights, goals, and measurements survive. Version 1.0 would have dropped all of them.

Automated testing and continuous integration. The project now has 87 automated tests. These include JUnit tests for the security and validation logic and for every ViewModel, run against an in-memory fake repository and a controllable clock. Robolectric tests build a real version 1 database and prove that the upgrade preserves its data. Robolectric UI-flow tests drive the screens with Espresso, including a test that saves a weight, reaches the goal, and confirms that a private notification was posted. A GitHub Actions workflow runs Android Lint, the build, and every test on each push and pull request. In the final run, all 87 tests passed and lint reported zero errors.

Course Outcomes

In Module One, I planned for this enhancement to demonstrate Outcome 4, using well-founded techniques and tools, as its primary outcome, and Outcome 5, a security mindset, alongside it. Both were met. For Outcome 4, the MVVM architecture, the Repository pattern, constructor injection, background threading, Jetpack ViewModel and LiveData, automated tests at three levels, and continuous integration are industry-standard techniques applied to a real codebase without losing any feature. For Outcome 5, each security change in Table 1 closes a specific vulnerability identified in the code review, and each change is verified by a test rather than by inspection alone.

The enhancement also advances two outcomes I had planned to address mainly in other parts of the ePortfolio. Version 2.0 supports Outcome 1, building collaborative environments: the CI workflow checks every pull request automatically, the README documents the architecture for other developers, and the file headers and comments explain why each design decision was made. For Outcome 2, professional communication, this narrative, the before-and-after table, and the README are written for both technical reviewers and potential employers.

I have three updates to my outcome-coverage plan. First, I raised the minimum Android version from API 24 to API 26, because the platform's PBKDF2WithHmacSHA256 implementation is only available from API 26. The alternative was hand-writing a key derivation function, a form of custom cryptography that secure coding standards advise against, so the trade-off favored a vetted platform primitive at the cost of a small share of very old devices. Second, I added Robolectric, which was not in the plan. It lets the UI-flow and database-migration tests run on the JVM in CI without an emulator. Third, the authentication columns now arrive in schema version 2 through SQLiteOpenHelper, so the Room migration in Enhancement Three will become version 2 to version 3. Database encryption with SQLCipher remains in Enhancement Three, as planned. Outcome 3, algorithmic principles and trade-offs, is still covered mainly by Enhancement Two.

Reflection on the Enhancement Process

The most important lesson was that architecture is what makes software testable. In version 1.0, the goal-reached rule lived inside an Activity method that also set text colors, so the only way to check it was to run the app and look. Once the rule moved into a plain GoalSummary class and the ViewModels depended on an interface, the same logic could be checked in milliseconds with no device. The 87 tests exist because the design allowed them, and they repeatedly caught regressions while the refactor was in progress.

The security work showed how much depends on details that a demonstration never reveals. Hashing a password is easy. A secure login also requires a unique salt, a deliberately slow algorithm, a constant-time comparison, a lockout that cannot be used to test guesses while it is active, equal timing for unknown and known usernames, and an upgrade path for users whose old hashes are already in the database. The legacy upgrade was the most instructive constraint. The plaintext password exists only at the moment the user types it, so the moment of a successful login is the only point where a weak hash can safely be replaced.

The work also involved several technical challenges. The first was that 600,000 PBKDF2 iterations take on the order of a second on a phone, which would freeze the login screen on the main thread. Moving the work to a background executor, and disabling the buttons while it runs, solved that and made the threading model concrete rather than theoretical. The second challenge was platform behavior that did not match its name. allowBackup="false" does not stop device-to-device transfer on Android 12 and later, so the data extraction rules had to exclude the database explicitly. In the same way, SQLite on API 26 cannot drop a column, so the phone number column is emptied now and will be removed when Room rebuilds the table. The third challenge was testing asynchronous code. Espresso waits for the main thread but not for my background executor, so the UI tests poll for their expected result. The first run also failed three of 86 tests because Robolectric's default screen was too small for Espresso to tap the login buttons and because one test opened the wrong menu. Both were test setup problems rather than application defects, and the second run passed all 86 tests. A final review before submission found one more gap. If the screen was left on past the 15-minute limit, the next tap refreshed the timer instead of ending the session, because the session was only checked when a screen opened or resumed. I changed SessionManager so an expired session can no longer be refreshed, made SecureActivity check the session at the start of every touch, and added a test for that case, which brought the suite to 87 tests. I also made the login screen recover from a database error instead of leaving its buttons disabled. The lesson was that a timeout is only as strong as the places where it is checked.
